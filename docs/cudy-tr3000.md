# Cudy TR3000 256MB v1: zapret2 и VLESS

Настройка выполнена 29 октября 2026 года, Cloudflare Tunnel доработан 30 октября.
Это **Cudy TR3000 256MB v1**
(`cudy,tr3000-256mb-v1`): 256 MB NAND и 512 MB RAM. Образ для обычной
версии TR3000 с другим размером flash не подходит.

## Куда направляется трафик

| Назначение | Обработка |
| --- | --- |
| YouTube, Googlevideo, Ytimg, необходимые API/аватары | Прямое соединение + zapret2 |
| Discord, CDN и выделенные порты голосовых соединений | Прямое соединение + zapret2 |
| Instagram и связанные Meta CDN | Прямое соединение + zapret2 |
| X / Twitter и Twimg | Прямое соединение + zapret2 |
| Веб-трафик к официальным IPv4-диапазонам Cloudflare | Прямое соединение + zapret2, адреса из прямого Cloudflare DoH |
| Cloudflare Tunnel: TCP/UDP 7844, служебный HTTPS `trycloudflare.com` | Прямое соединение + отдельные профили zapret2 |
| Telegram: домены и IPv4-сети из geosite/geoip | Через VLESS |
| ChatGPT / OpenAI и Claude / Anthropic | Через VLESS |
| Notion, включая изображения и вложения на доменах Notion | Через VLESS |
| Остальное | Прямое соединение |

PassWall2 использует шунтирующий узел `split` с Direct по умолчанию,
правилами `Telegram`, `AI`, `Notion` и выключенными `Cloudflare` / `VPNFallback`. FakeDNS отключён.
Пустое правило нельзя назначать на VPN: без условий оно может совпасть со всем
оставшимся трафиком. `VPNFallback` пока не назначен никакому узлу.
Результаты прямого DNS записываются в nftset, чтобы последующие соединения
могли обходить пользовательское ядро Xray.

31 октября добавлено правило `Notion` для `notion.com`, `notion.so`,
`notion.site`, `notionusercontent.com`, `notion-static.com` и их поддоменов.
С Windows через прямой маршрут запросы к приложению и картинкам зависали;
через действующий 3x-ui/WARP тестовое изображение возвращало HTTP 200.
После применения правила с Windows проверены `app.notion.com` (HTTP 200)
и `/images/page-cover/gradients_2.png` на `www.notion.so` (HTTP 200, 135875 байт);
`img.notionusercontent.com` также отвечает вместо тайм-аута.
После смены маршрута уже открытый Notion продолжал получать Cloudflare HTTP 403
на запросы `/api/v3/`, а база показывала `Something went wrong` даже после Reload.
Полный выход через меню приложения **File → Exit** и повторный запуск восстановили
загрузку базы и изображений. Перед изменением серверного выхода проверьте приложение
с заново установленными соединениями; проверки только главной страницы недостаточно.
Для существующей настройки применяется
[notion-vpn.sh](../configs/cudy-tr3000/notion-vpn.sh): скрипт сохраняет
`/etc/config/passwall2` в `/root/notion-routing-backup.XXXXXX/passwall2`,
добавляет правило и перезапускает PassWall2 и DNS. Настройки 3x-ui не меняются.
Для отката только этого маршрута удалите `passwall2.split.Notion` и
`passwall2.Notion` через `uci delete`, выполните `uci commit passwall2`,
перезапустите PassWall2 и dnsmasq.

Cloudflare определяется по 15 официальным IPv4-диапазонам, сверенным с
<https://www.cloudflare.com/ips-v4> 29 октября 2026 года. Официальный список
не обещает покрытие любого BYOIP/специального сервиса.
Zapret2 также не отменяет географические ограничения самого сайта; такие домены
можно отдельно добавить в `VPNFallback`.

Для `macro.vzl0m.com` прежний DNS через VPN выдавал `188.114.96.3` /
`188.114.97.3`. Изолированная проверка с обходом PassWall2 и захватом на WAN
показала исходящие SYN и повторы, без SYN-ACK. Поэтому одной смены текущей
TLS-стратегии для этих адресов недостаточно. Причина отсутствия ответов
за пределами Cudy этой проверкой не установлена.

Решение без VPN для веб-трафика: **прямой Cloudflare DoH** выдаёт для того же
имени `104.21.77.110` / `172.67.207.48`, и оба адреса доступны с текущим zapret2.
Это штатные DNS-ответы с TTL, а не закрепление вручную выбранного IP.
Google DoH с ECS `8.8.8.0/24` и без него продолжал выдавать недоступные адреса.
Временная подмена DNS для `macro` удалена, общее VPN-правило Cloudflare выключено.
Исходные URL, Host/SNI и проверка сертификата сохранены. Состав DNS-ответов
может меняться, поэтому результат не является гарантией всех сайтов навсегда.

Прямой режим включает [activate-direct-doh.sh](../configs/cudy-tr3000/activate-direct-doh.sh)
после установки и запуска двух DNS-служб, описанных ниже.
[cloudflare-vpn.sh](../configs/cudy-tr3000/cloudflare-vpn.sh) сохранён только как
ручной резервный вариант: он снова направит официальные диапазоны через VPN.
Автоматического VPN-fallback нет.

## Стратегии zapret2

Основная конфигурация — адаптация Flowseal ALT9 на Lua-функции **nfqws2**:

- YouTube: `hostfakesplit`, подставной host `www.google.com`, 4 повтора,
  timestamp fooling.
- Общий список: `hostfakesplit`, `ozon.ru`, 4 повтора, timestamp + MD5 fooling.
- Cloudflare HTTPS: отдельный приоритетный IP-профиль TLS fake Google,
  12 повторов, timestamp fooling. Для HTTP остаётся `hostfakesplit`.
- Tunnel: TCP/7844 — TLS fake Google, 12 повторов; UDP/7844 — fake QUIC,
  6 повторов. HTTPS `trycloudflare.com` также имеет профиль TLS fake.
- **X имеет приоритетное исключение:** TLS fake Google, 12 повторов,
  timestamp fooling. Оно перенесено из местного Zapret Local: общий ALT9
  временами останавливался после первых 12 KB страницы X.
- QUIC: fake Google QUIC Initial, 6 повторов.
- Discord voice control: TLS fake Google, 12 повторов, timestamp fooling
  для `discord.media` на TCP 2053, 2083, 2087, 2096, 8443.
- Discord/STUN: fake Google QUIC Initial, 6 повторов на UDP 19294–19344
  и 50000–50100. Здесь исключение VPN задаётся **только по IP**:
  `--hostlist-exclude` тоже требует hostname и не позволяет выбрать профиль
  для Discord IP discovery/STUN, в которых доменного имени нет.

30.10.2026 исправлены два отдельных сбоя голоса: зависание управляющего
WebSocket на TLS и невыбираемый UDP-профиль из-за доменного фильтра.
В захвате после исправления видны шесть QUIC fake по 1200 байт перед
74-байтовым запросом IP discovery; раньше уходил только сам запрос.
В реальном звонке появились входящие аудиопакеты от двух участников,
RTT около 100 мс, пользователь подтвердил работу звука, в том числе после
повторного входа в канал. После нового подключения отмечен отдельный UDP
ping timeout с последующим ответом за 109 мс; отсутствие потерь пакетов
не заявляется. Голос остаётся прямым, без VPN; это проверка данного звонка,
не всех регионов Discord.

Перехватываются только начальные пакеты соединений: TCP 20 исходящих / 10
ответных, UDP 5 / 3. Flow offloading отключён. Общий перехват игровых портов,
автоматическое включение всех доменов и большие списки блокировок не включены.

Windows BAT-файлы не запускаются на роутере. Использованы техники и бинарные
шаблоны из ревизии Flowseal
`176f56dc3f11ce5915c26abcdde903f93d835b64`.
Сохранены также кандидаты `config.alt11` и `config.exp`; их параметры проверены
`--dry-run`, но успешная проверка синтаксиса не означает работоспособность
на конкретном провайдере. Активен ALT9 с отдельным правилом X.

Списки и конфигурация находятся в `/opt/zapret2/`. Генератор:
[make-zapret.py](../configs/cudy-tr3000/make-zapret.py).

## Совместимость служб и DNS

Адрес VPN исключён и из zapret2, и из проксирования PassWall2. Поэтому уже
работающий v2rayN на Windows продолжает соединяться с сервером напрямую.
Список IP сервера обновляется перед применением правил zapret2, с сохранением
последнего рабочего значения при ошибке DNS.

Пакеты, созданные nfqws2, сохраняют старшие биты отметки zapret2 и получают
младший байт `0xff`, который PassWall2 исключает из повторного перехвата.
Обычные прямые соединения Xray при этом могут проходить обработку zapret2.
Это делает [zapret-guard.sh](../configs/cudy-tr3000/zapret-guard.sh).

Служба `vpn-dns` запускает второй небольшой экземпляр Xray:

- `127.0.0.1:15353`: приём DNS TCP/UDP, пересылка к Cloudflare `1.1.1.1`
  **по TCP** внутри VLESS (отдельные UDP-запросы терялись);
- `127.0.0.1:18080`: HTTP-прокси через VPN для диагностики;
- `127.0.0.1:18081`: SOCKS-прокси через VPN для диагностики.

Все эти порты доступны только самому роутеру. Дополнительно работают:

- `https-dns-proxy` 2026.05.06-r1 на `127.0.0.1:15354`: прямой DoH к
  `https://1.1.1.1/dns-query`, с проверкой TLS, IPv4, без DNS-bootstrap по имени.
  Его автоматическое редактирование dnsmasq и перехват клиентского DNS отключены.
  Конфигурация: [direct-doh.config](../configs/cudy-tr3000/direct-doh.config).
- `dns-select` на `127.0.0.1:15355`: отдельный dnsmasq только для DNS,
  кэш 1000 записей, по умолчанию сервер `15354`. Для доменов Meta
  (`instagram.com`, `cdninstagram.com`, `fbcdn.net`, `facebook.com`, `fbsbx.com`,
  `ig.me`) используется прежний сервер `15353`: прямой DoH выбирал недоступный
  Instagram edge `157.240.205.174`, прежний DNS — рабочий `57.144.244.34`.
  Это исключение только для DNS; веб-трафик Meta остаётся прямым.
  Файлы: [dns-select.conf](../configs/cudy-tr3000/dns-select.conf),
  [dns-select.init](../configs/cudy-tr3000/dns-select.init).

Прямой DNS PassWall2 и основной dnsmasq используют `15355`. DNS проксируемых
доменов AI/Telegram остаётся DoH через VPN-узел. Имя самого VPN-сервера
разрешается отдельно через Zyxel, что устраняет циклическую зависимость.
Обычный DNS теперь не зависит от VPN; исключения Meta и проксируемые сервисы
зависят. Неявного отката к DNS провайдера для остальных имён нет.

Порядок запуска: основной dnsmasq, `https-dns-proxy` S20, zapret2 S21,
vpn-dns S25, dns-select S26, PassWall2 S99. Перед чистым восстановлением нужно
установить пакет `https-dns-proxy`; одной резервной копии его конфигурации мало.

WAN IPv6 и объявления IPv6 в LAN отключены, AAAA фильтруются. Это исключает
необработанный IPv6-маршрут при текущей IPv4-конфигурации. Для включения IPv6
понадобится отдельно настроить оба механизма и повторить проверки.

## Проверки

На роутере [smoke.sh](../configs/cudy-tr3000/smoke.sh) выполняет полные GET,
а не только получение HTTP-заголовков. Проверены:

- YouTube ~960 KB, обложка Ytimg 21 KB;
- Discord ~170 KB и API gateway;
- Instagram ~372 KB;
- X ~45 KB и JavaScript Twimg ~17 KB;
- Cloudflare ~1.3 MB;
- Telegram Web.

До zapret2 YouTube, Discord, Instagram и X не проходили проверку.
После настройки все перечисленные GET завершались с HTTP 200.
Cloudflare trace, в том числе у `macro.vzl0m.com`, показывает RU / warp=off
на прямом соединении, а диагностический HTTP-прокси — DE через VLESS.
Временно проверенный режим всего Cloudflare через VPN снова выключен.

Дополнительно проверен **пересылаемый LAN-трафик**: временный клиент в network
namespace подключался через `br-lan`, NAT и те же правила, что устройства Wi-Fi.
Первоначальные семь GET (YouTube, обложка, Discord, Instagram, X, Cloudflare,
Telegram) прошли с HTTP 200. В актуальный тест добавлен `macro.vzl0m.com`,
выход Cloudflare ожидается напрямую, RU. Тестовый интерфейс, адрес и namespace
удалены автоматически. Скрипт —
[forwarding-smoke.sh](../configs/cudy-tr3000/forwarding-smoke.sh), требуется `kmod-veth`.
После включения прямого DoH с сохранением прежнего DNS для Meta проверка
всех восьми адресов со стороны LAN завершилась HTTP 200; Cloudflare trace показал RU.
JavaScript (~687 KB) и CSS (~91 KB) `macro.vzl0m.com` также загрузились полностью.

Короткая сравнительная загрузка 5 MB с `speed.cloudflare.com/__down`:
прямое соединение 0.944 с (~42 Мбит/с), через VPN 1.624 с (~25 Мбит/с).
Это единичная прикладная проверка с учётом установления соединения,
не предельная пропускная способность маршрутизатора или тарифа.

### Cloudflare Tunnel

Tunnel работает напрямую через zapret2; специального VPN-правила для 7844 нет.
Добавлены отдельные профили TCP/UDP 7844 и HTTPS `trycloudflare.com`.
Ранее соединения регистрировались, но затем зависали/переподключались;
API создания Quick Tunnel также мог зависать на TLS. Профиль TLS fake вместо
hostfakesplit восстановил HTTPS API и проверенные адреса Cloudflare/Discord.

Для `trycloudflare.com` основной и PassWall2 dnsmasq используют напрямую
локальный DoH-сервис `15354`, обходя DNS-кэш Xray. Отрицательное кэширование
dnsmasq отключено, чтобы первоначальный NXDOMAIN не удерживался после появления
новой записи. Создание новой записи у провайдера всё равно может занять несколько
секунд. Настройку применяет [tunnel-dns.sh](../configs/cudy-tr3000/tunnel-dns.sh).

Проверен `cloudflared 2026.9.1` на Windows без v2rayN/Xray/sing-box на компьютере,
через Ethernet и Cudy. После исправления отдельные HTTP/2 и QUIC прошли по
60 секунд запросов без ошибок после установления соединения (30 и 29 ответов).
QUIC первоначально ожидал появления нового DNS-имени; затем не переподключался.
Использовались обычный системный DNS и стандартная проверка TLS.

Финальная проверка `auto` выбрала QUIC: 180 секунд, 74 успешных контрольных
ответа, одна регистрация соединения, без транспортных ошибок и переподключений.
Прошли скачивание 2 MiB, загрузка 512 KiB с проверкой SHA-256 и 20 секунд простоя.
При появлении свежего Quick Tunnel имени было три начальных ошибки DNS;
после разрешения имени ошибок не было. Обычный запуск не требует `--wait-dns`,
подмены IP или отключения TLS-проверки. Дополнительно все восемь LAN smoke GET
прошли с HTTP 200, Cloudflare trace подтвердил прямой выход RU.

Тестовый сервер слушает только loopback, отдаёт случайную контрольную строку
и тестовые байты; пользовательские файлы не публикуются. Скрипт:
[check-cloudflare-tunnel.py](../configs/cudy-tr3000/check-cloudflare-tunnel.py).
Режим `--bulk` дополнительно проверяет скачивание 2 MiB, загрузку 512 KiB
с проверкой SHA-256 и паузу 20 секунд. Тестовые процессы автоматически
останавливаются. Журналы остаются в закрытом каталоге задачи, `tunnel-check*`.
Именной production-туннель с пользовательскими credentials не создавался.

HTTP-проверки **не подтверждают** полноценный голос Discord/Telegram,
воспроизведение видео, все CDN и QUIC в каждом приложении. Эти проверки
проводятся на клиенте без собственного VPN. Telegram P2P-звонок может уйти
на IP собеседника вне сетей Telegram; для гарантированного VPN-маршрута
звонков в настройках Telegram отключается Peer-to-Peer.

После установки доступно примерно 280 MB RAM и более 140 MB overlay.
Большие файлы установщика лежали в `/tmp` и исчезают после перезагрузки.

## Управление

VPN-правила: **Services → PassWall 2 → Shunt Rule**.
VPN-профиль сейчас статический: один узел извлечён из подписки, автоматическое
обновление подписки не настроено. PassWall2 имеет Node Subscribe, но смена узла
должна также обновить `/etc/vpn-dns.json`, имя VPN в bootstrap DNS и исключения
zapret2. Эти части пока не синхронизируются автоматически. Отдельной LuCI-панели
zapret2 нет; стратегии и списки редактируются по SSH.

Чтобы добавить исключение, откройте `Manual VPN exceptions`, внесите строку
`domain:example.org`, назначьте правилу узел `VLESS Reality Firefox`, затем
Save & Apply. Не назначайте VPN пустому правилу. Более узкий домен обычно лучше, чем
перенос целого CDN. Не включайте глобальный VPN, если нужна текущая схема.

SSH со служебным ключом с этого компьютера:

```powershell
& "$taskState\venv\Scripts\python.exe" -X utf8 configs/cudy-tr3000/router.py `
  --state-dir $taskState --command 'sh /root/cudy-smoke.sh'
```

Ключ сервера проверяется **до аутентификации**. Опция `--trust-new-board`
предназначена для проверенного перехода между прошивками, не для обхода
неожиданной смены SSH-ключа.

Команды на роутере:

```sh
/etc/init.d/zapret2 status
pidof xray
logread -e nfqws2
tail /tmp/log/passwall2.log
cat /proc/net/netfilter/nfnetlink_queue
sh /root/cudy-smoke.sh
```

`zapret2` и `vpn-dns` контролируются procd с перезапуском при падении;
PassWall2 использует штатный монитор. Все три службы включены в автозапуск.
Постоянная запись всех соединений Xray в файл выключена, чтобы лог не рос в RAM.
Для диагностики можно временно включить **Log → Enable Node Log** в PassWall2.
Отключать v2rayN на Windows для первых проверок не требуется: удобнее проверить
с телефона. Пока v2rayN включён, результат браузера на этом ПК может определяться
его собственными правилами, поэтому он не доказывает работу обхода на роутере.

## Резервные копии и откат

В закрытом каталоге `$taskState` сохранены:

- штатная конфигурация Cudy;
- сырые разделы BL2, u-boot-env, Factory, bdinfo, FIP;
- официальный промежуточный образ Cudy и конечный образ OpenWrt;
- `cudy-configured.tar.gz` с настроенной системой;
- ключ SSH, отдельный пароль администратора, исходные данные VPN;
- `RECOVERY.txt` с действиями без интернета.

SHA-256 конечного образа OpenWrt:
`1c022e987da0c7662d639cc9ae3d728d94cdba2a63a46a054313eecc44fae33c`.
Переход выполнен через официальный Cudy intermediate, затем `sysupgrade -n`.
Разметка загрузчика не менялась.

`/etc/sysupgrade.conf` включает `/opt/zapret2`, `/opt/xray` и локальную службу DNS.
Обычная резервная копия настроек не заменяет установку APK-пакетов после чистой
прошивки. Не переносите её вслепую на другую версию ядра или другой роутер.

Чтобы временно вернуть обычный интернет с DNS провайдера, выполнить по SSH:

```sh
/etc/init.d/passwall2 stop
/etc/init.d/zapret2 stop
uci set dhcp.@dnsmasq[0].noresolv=0
uci -q delete dhcp.@dnsmasq[0].server
sed -i '\|^server=/trycloudflare.com/127.0.0.1#15354$|d' /etc/dnsmasq.conf
uci commit dhcp
/etc/init.d/dnsmasq restart
```

Эти команды оставляют LAN, Wi-Fi и SSH доступными. Они не отключают автозапуск:
для длительного отката дополнительно выполнить `disable` у служб zapret2,
passwall2, vpn-dns, dns-select и https-dns-proxy.
Не запускайте повторно `recover_lan.py` в обычной работе: это помощник для
заранее подготовленного перехода прошивки с временным изменением IPv4 Windows.

Проблема в #3193 относится к TLS ClientHello / uTLS и ML-KEM, а не к строке
HTTP User-Agent браузера. Поэтому смена HTTP-заголовка её не исправляет.
Выбран актуальный Xray с `firefox`, и его соединение с данной подпиской
проверено на самом роутере. Значение `support-x25519mlkem768` из подписки
не копируется как выдуманный параметр Xray: это специфичный параметр Mihomo.

Основные зависимости установлены из подписанных индексов OpenWrt/PassWall.
GitHub APK PassWall2 26.10.29 проверен по SHA-256 официального release asset,
но его подпись не принималась ключом feed; только этот локальный APK был
установлен с `--allow-untrusted`. Локальный комплект dnsmasq-full предварительно
скачан через `apk fetch` по проверенному индексу; при офлайн-замене dnsmasq
также понадобился этот флаг. Проверка TLS и подписей feeds глобально не отключена.
