# Battlefield 6: повторная диагностика 13 октября 2026

**Диагностика остановлена по просьбе пользователя; текущая схема его устраивает.** [Сохранённое состояние и продолжение](network-checkpoint-20261013.md). WireGuard на сервере и рабочие локальные процессы сохраняются. Описанные ниже следующие проверки — возможные направления, не текущие запущенные действия.

Подтверждены редкие большие задержки **внутри компьютера, между Ethernet и sing-box TUN**. Это может объяснять сообщённые пользователем скачки игрового пинга примерно с 80 до 200 мс. Причина всех показаний игрового индикатора не установлена: точной синхронной записи LAT игры нет, внешний путь отдельно полностью не исследован.

## Состояние перед проверкой

Windows, Ryzen 5 5600 (12 логических процессоров), v2rayN 7.24.9, sing-box 1.13.12, TUN `mixed`. Активен экспериментальный профиль WARP → WireGuard, SOCKS `127.0.0.1:19506`. Но игровые UDP-соединения Battlefield совпадают с `port_range=0:65535 => route(direct)`: **игра проходит через локальный TUN, затем непосредственно в интернет**, минуя WARP, WireGuard и VLESS.

Сохранённый 9 октября `CpuPriorityClass=6` в IFEO продолжает работать. Основной sing-box действительно имеет AboveNormal (Win32_Process.Priority=10), Battlefield — Normal (8). Значение проверено у работающего процесса, а не только в реестре. Предыдущий диагноз и эксперимент Normal → AboveNormal → Normal описаны в [инструкции v2rayN](v2rayn-routing.md).

Физический интерфейс Ethernet имеет индекс 7, текущий singbox_tun — 22. Старый индекс 20 из диагностики 9 октября использовать нельзя. Основной игровой адрес в свежих пакетах — `5.60.100.239:21339`, вспомогательные — `18.199.104.251:21005`, `3.66.235.248:21004`. Clash API продолжает показывать старый `5.60.100.54:21193` у переиспользуемой UDP-ассоциации: его нельзя считать достоверным адресом текущего матча.

Фильтры запущенного zapret: TCP 80/443/2053/2083/2087/2096/8443/12; UDP 443/19294–19344/50000–50100/12. Наблюдаемые игровые порты в эти диапазоны не входят. Настройки zapret не менялись.

## Измерения

Пассивный WinDivert `SNIFF | RECV_ONLY | NO_INSTALL`, существующая DLL zapret. Пакеты не блокируются и не перенаправляются. Использованы временные метки ядра, SHA-256 полного UDP payload, направление, удалённый IP/порт и длина; локальный порт физической копии может отличаться из-за NAT. Неоднозначные повторения исключаются. Игровые пары подтверждены локальными портами процесса bf6 на стороне TUN.

| Проверка | CPU, медиана | Входящие: p95 / p99 / максимум | Исходящие: p95 / максимум |
| --- | ---: | ---: | ---: |
| Исходная, 120 с, AboveNormal | 94,5% | 25,84 / 139,64 / 371,86 мс | 3,89 / 41,26 мс |
| После сообщённого включения лимита 60 FPS, 120 с | 99,1% | 21,69 / 70,15 / 161,90 мс | 4,77 / 25,56 мс |

Пользователь подтвердил включение 60 FPS, но фактическая частота кадров не записывалась. CPU не разгрузился, поэтому это **не доказывает эффективность ограничения FPS**. Разные участки матча и отсутствие обратной фазы также мешают приписать уменьшение максимума только этой настройке.

Одновременно отправлялись STUN-запросы к одному серверу Cloudflare, 20 и 1280 байт: обычная маршрутизация через TUN и сокеты, явно привязанные к физическому интерфейсу через IP_UNICAST_IF. В исходных 120 с максимумы прямых запросов — 74,99/79,04 мс, через TUN — 371,56/152,54 мс. Таймаутов нет (по 80 запросов каждого вида). Это контрольный внешний сервер, не игровой RTT; задержка чтения сокета самим измерителем тоже может зависеть от CPU.

Затем при работающем матче проверен тот же процесс sing-box, без разрыва соединений:

| Фаза | CPU, медиана | Входящие p95 / максимум | Исходящие p95 / максимум |
| --- | ---: | ---: | ---: |
| AboveNormal до, около 45 с | 98,9% | 27,13 / 199,44 мс | 4,58 / 18,44 мс |
| High, около 45 с | 99,9% | 27,36 / 234,41 мс | 0,43 / 15,40 мс |
| AboveNormal после, около 60 с | 99,85% | 34,67 / 489,58 мс | 4,85 / 30,13 мс |

High заметно улучшил исходящие пакеты, но не устранил большие входящие задержки. Постоянный High не установлен: исходный AboveNormal автоматически восстановлен и проверен. Реестр не изменялся. Нельзя по этому тесту определить, какой именно компонент Windows/TUN задерживает входящие пакеты: это локализация участка, а не доказательство дефекта одного конкретного потока sing-box.

В трёх захватах 102 423 копии пакетов. Несопоставленные копии не считаются потерями игры: среди них физические контрольные STUN-пакеты, которым и не положено проходить через TUN, а также другие UDP-потоки. Таймаут ICMP от игрового сервера (15/15) тоже не доказывает потерю игрового UDP: сервер может не отвечать на ping.

Пользователь затем подтвердил: без TUN, с `Set system proxy`, Battlefield работает стабильно. В локальных настройках также проверено `EnableTun=false`. Это пользовательское наблюдение, без синхронного захвата или числовой записи LAT в этой фазе. Оно поддерживает локализацию проблемы в пути через TUN; постоянное выключение TUN не соответствует требованию пользователя.

Затем предложено переключить только `Stack: mixed → system`. В установленном sing-box 1.13.12 `mixed` использует system для TCP и gVisor для UDP, поэтому переход на system меняет обработку игровых UDP-пакетов. Пользователь сообщил о потере связи в Battlefield и индикаторе `-1 ms` после переключения; тест не дал рабочего результата. Возвращено пользователем: `Stack=mixed`, `EnableTun=false`, `Set system proxy`. Повторно применять system ко всему трафику на основании одной только документации нельзя.

Описание стеков: [sing-box TUN stack](https://sing-box.sagernet.org/configuration/inbound/tun/#stack). Документация новых версий также описывает изменения 1.15; они не относятся к установленному 1.13.12.

### Отдельный сбой проверки доступности v2rayN

В GUI-логе в 18:01:56 и 18:03:08 МСК записан `WaitForProxyPort Timeout waiting for proxy port 10808 to be ready`. Это ошибка ожидания готовности локального прокси при перезапуске; имеющегося лога недостаточно, чтобы приписать её конкретному сетевому стеку.

После возврата к mixed с выключенным TUN проверены:

- SOCKS `19506`: Cloudflare trace возвращает немецкий выход `138.124.114.237`.
- Основной SOCKS/HTTP `10808`: Google generate_204 отвечает HTTP 204; OpenAI models без токена — ожидаемый HTTP 401. Лог отдельного WireGuard-клиента подтверждает запрос OpenAI через `endpoint/wireguard`.
- Нижняя строка v2rayN `The delay: -1 ms, none` — результат `ConnectionHandler.RunAvailabilityCheck`, который обращается к настроенному Google generate_204 через основной локальный SOCKS. По текущим правилам Google идёт `direct`; это не измерение RTT до немецкого сервера. При ошибке HTTP-проверки возвращается -1. Повтор такого запроса с .NET SocketsHttpHandler дал сначала отмену запроса, затем HTTP 204 за 1279 мс. Причина нестабильности именно этого запроса ещё не установлена.
- `IPAPIUrl=null`, поэтому `none` в той же строке не свидетельствует само по себе об отсутствии иностранного выхода. Тест выбранной строки профиля и проверка в нижней строке используют разные пути.

Источник поведения интерфейса: [ConnectionHandler.cs, v2rayN 7.24.9](https://github.com/2dust/v2rayN/blob/7.24.9/v2rayN/ServiceLib/Handler/ConnectionHandler.cs), [StatusBarViewModel.cs](https://github.com/2dust/v2rayN/blob/7.24.9/v2rayN/ServiceLib/ViewModels/StatusBarViewModel.cs).

Сохранены [частичные результаты](../experiments/results/2026-10-13-battlefield/isolated-stacks-partial.json) и [проверка уборки](../experiments/results/2026-10-13-battlefield/isolated-stacks-cleanup.json).

Исключения игровых IP/подсетей отвергнуты пользователем: адреса меняются, решение должно работать и с другими играми. Требование macOS сохраняется, но сначала отлаживается Windows.

Следующий кандидат — официальный клиент WireGuard с системным интерфейсом → локальная передача WireGuard UDP через WARP → существующий немецкий сервер. Это заменяет обработку IP-пакетов в v2rayN TUN, однако WARP-транспорт и локальные ретрансляторы остаются пользовательскими процессами. Улучшение задержек не гарантируется; перевод всех игр на иностранный выход также может увеличить обычный RTT относительно прямого соединения.

Для проверки добавлены отдельные peers `10.203.13.4/32` (Windows) и `.5/32` (macOS) на существующий экспериментальный `wg-codex`. VLESS и прежние peers не перезапускались. Первый профиль содержит **только `AllowedIPs = 10.203.13.1/32`**, без DNS и default route; UDP relay использует отдельный локальный порт `19515`. `native-wg-probe.ps1` ограничивает время работы тестового интерфейса и удаляет его в `finally`. `compare-native-wg.py` сравнивает новый клиент и существующий SOCKS `19506` на одном частном UDP echo, с одинаковыми пакетами и чередованием порядка.

Официальный Windows WireGuard 1.1.1 установлен с `DO_NOT_LAUNCH=1`; цифровая подпись WireGuard LLC действительна, MSI завершился с кодом 0. SHA-256 установщика: `7BFED60AD61B785C914B38B61555A975488E1D3EC472DBFB2FCDF498FCA75242`. После отменённого запроса UAC пользователь разрешил повтор; тестовый tunnel service успешно запущен в 19:03 МСК.

### Первый замер native WireGuard без игры

В момент проверки процесса Battlefield уже не было. За 60 секунд отправлено по 171 UDP-запросу размером 1024 байта; порядок двух путей чередовался, WARP-транспорт и серверный echo общие. Медиана общей загрузки CPU — 33,71%.

| Клиент | Медиана | p95 | p99 | Максимум | Таймауты |
| --- | ---: | ---: | ---: | ---: | ---: |
| Официальный Windows WireGuard | 98,18 мс | 107,29 мс | 112,89 мс | 116,12 мс | 0/171 |
| Прежний sing-box WireGuard через SOCKS 19506 | 99,49 мс | 112,46 мс | 123,94 мс | 151,20 мс | 0/171 |

[Полные результаты серии](../experiments/results/2026-10-13-battlefield/native-wg-idle.json). Основной v2rayN TUN в обоих случаях выключен: это сравнение клиентов WireGuard, а не полное воспроизведение прежнего пути через v2rayN TUN. Разница обычного RTT мала, а меньшее максимальное значение в одной короткой серии не доказывает устранение игровых скачков. Требуется повтор под игровой нагрузкой и затем проверка маршрутизации всего трафика.

Через 180 секунд тестовый service и его маршрут автоматически удалены. Проверка подтвердила отсутствие оставшегося service/маршрута и неизменность default routes. Пользователю предложено войти в матч с прежними `TUN off` / `Set system proxy` для следующего изолированного замера; игровой маршрут пока не менялся.

Скрипты подготовки не являются готовым full-tunnel решением. Перед общим включением остаются проверки DNS, IPv6, физического маршрута внешнего WARP-соединения, восстановления после смены сети, остановки транспорта и задержек игры под нагрузкой. В официальном Windows-клиенте `/0` включает ограничения firewall, которые могут заблокировать внешний процесс WARP; механическое использование `/1` вместо `/0` снимает эту защиту и само по себе не решает DNS/IPv6. См. [WireGuard Windows network quirks](https://git.zx2c4.com/wireguard-windows/about/docs/netquirk.md) и [управление tunnel service](https://git.zx2c4.com/wireguard-windows/about/docs/enterprise.md).

Для macOS есть официальный WireGuard и сборки usque, но испытаний на Mac пока нет. `usque nativetun` в 4.2.1 macOS не поддерживает; выбранная схема использует `usque socks` с UDP. В `physical_proxy.py` подготовлено связывание сокета через Darwin `IP_BOUND_IF`, вместо Windows `IP_UNICAST_IF`; проверен выбор параметров на mock-сокетах, не реальная работа macOS. Источники: [WireGuard Apple](https://git.zx2c4.com/wireguard-apple/about/), [usque 4.2.1](https://github.com/Diniboy1123/usque/releases/tag/v4.2.1), [Apple IP_BOUND_IF](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/netinet/in.h).

### Нагрузка игры, вечерний маршрут и приоритет транспорта

Пользователь уточнил конечную политику: **игры напрямую, заблокированное через иностранный VPN**. Поэтому общий default route через системный WireGuard не выбран: он изменил бы маршрут игр. В `configPre.json` прямое игровое соединение обрабатывается самим sing-box через outbound `direct`, а не основным Xray или WARP. Изменение приоритета WARP не является исправлением этого участка TUN.

При запущенной Battlefield и CPU около 100% первая 90-секундная серия дала native WARP→WG медиану 130 мс, p95 300 мс, максимум 586 мс, 2 таймаута из 185. Прежний userspace WG — 132 / 330 / 852 мс, 0/185. Измеритель тогда имел Normal; последующие серии использовали AboveNormal и пассивный захват временных меток ядра.

В серии с одним native-клиентом и переключением только endpoint (прямой UDP → WARP → прямой UDP) метки ядра дали:

| Путь | Медиана | p95 | Максимум |
| --- | ---: | ---: | ---: |
| Прямой, до | 234,03 мс | 275,49 мс | 301,92 мс |
| WARP | 114,03 мс | 160,67 мс | 211,32 мс |
| Прямой, после | 230,58 мс | 279,61 мс | 292,80 мс |

Это RTT до частного echo на VPN-сервере, **не игровой пинг**. WARP в данный вечер улучшает маршрут, но в прикладной WARP-фазе были 2 таймаута native и 4 userspace. В захвате три несопоставленных ключа; без серверного захвата они не локализуют место потери. Результаты — `route-*.json`, `route-kernel.json`.

Проверка Normal → High → исходные значения у процессов экспериментального WARP-транспорта (physical relay, usque, оба SOCKS UDP relay и userspace sing-box) дала следующие kernel RTT native WARP→WG:

| Фаза | Медиана | p95 | Максимум |
| --- | ---: | ---: | ---: |
| До | 115,13 мс | 219,22 мс | 556,94 мс |
| High | 102,19 мс | 126,54 мс | 525,89 мс |
| После | 122,08 мс | 239,09 мс | 593,37 мс |

CPU во всех фазах около 100%. Приоритет улучшил основную часть распределения, но большие отдельные задержки остались. Лаг чтения пассивного захвата: p99 0,271 мс, максимум 1,312 мс; эти kernel RTT не объясняются поздним чтением измерителем. Все пять исходных приоритетов восстановлены и проверены, High постоянно не устанавливался. Данные — каталог `high-priority/`. Предшествующая аналогичная серия AboveNormal сохранена в `priority-before.json`, `priority-above-normal.json`, `priority-after.json` и `transport-priority-*.json`.

Пользователь предупредил, что иногда делает Alt+Tab, после возврата игровой индикатор на пару секунд подскакивает. Время смены фокуса в этих сериях не записано; такие интервалы нельзя достоверно вычесть задним числом. Это ограничение сравнения фаз, а не доказанная причина всех сетевых выбросов. Игра во время этих опытов оставалась на прямом соединении с выключенным v2rayN TUN; пользователь не наблюдал прежней постоянной проблемы.

В диагностическом launcher исправлено недостаточное ожидание запуска/удаления Windows tunnel service: вместо асинхронного вызова и фиксированных трёх секунд используются ожидание завершения CLI и появления маршрута. Одна попытка пассивного захвата не стартовала из-за прежней гонки; её kernel-данных нет. Ещё одна подготовительная direct-серия не прошла warmup, поскольку ограниченный по времени серверный echo уже завершился: оба пути дали три таймаута, что не считается результатом сравнения. Завершённые серии проверены отдельно. По итогам удалены временные Windows tunnel services/маршруты, остановлены отдельный relay 19515 и серверный echo. Default routes не изменены. Установленный официальный WireGuard и приватные пробные конфиги сохранены; основной WARP→WG SOCKS 19506 и VLESS не удалялись.

**Статус:** рабочее исправление TUN для игр пока не подтверждено. Следующая проверка должна относиться к локальному `sing-box TUN → direct`, сохранять текущую политику маршрутизации и учитывать переключения фокуса. Результат native full-tunnel нельзя выдавать за решение этой задачи. Первая изолированная проверка `system` измеряла прикладной RTT обычным процессом при высокой нагрузке; для вывода именно о локальной задержке этого стека нужны метки пакетов на физическом и виртуальном интерфейсах.

### Основной TUN system, 20:06–20:08

После выхода из игры пользователь переключил основной v2rayN на `system` и включил TUN. Фактический inbound: system, MTU 9000, auto_route=true, strict_route=false. На простое работали прямой HTTPS, заблокированный OpenAI через прокси (ожидаемый HTTP 401 без авторизации), иностранный выход SOCKS 19506. ## Исходные данные и повторение

[Агрегаты захватов, контрольные пробы и времена фаз](../experiments/results/2026-10-13-battlefield/) сохранены в Git. Полные локальные метаданные захватов остаются в `%LOCALAPPDATA%\DeviceSetup\battlefield-20261013`; содержимое пакетов не сохраняется, только хеши. Ключи VPN и конфиги аккаунтов к этой диагностике не относятся и в Git не входят.

Перед повторением определить текущие индексы через `Get-NetAdapter`, порты bf6 через `Get-NetUDPEndpoint -OwningProcess <PID>`. В этом тесте игровые локальные порты — 54260/56136. Скрипт захвата также наблюдает удалённые UDP 21000–21999 и контрольный STUN 3478; для другого диапазона игровые физические копии могут не попасть в фильтр.

Из административного PowerShell (право нужно существующему драйверу WinDivert):

```powershell
python .\experiments\capture-tun-udp.py --seconds 120 --game-port 54260 --game-port 56136 --dll 'C:\ProgramData\ZapretTray\Versions\1.10.2\bin\WinDivert.dll' --output-directory 'C:\private\bf6-test'
```

В отдельном обычном PowerShell одновременно:

```powershell
python .\experiments\monitor-tun-latency.py --seconds 120 --physical-interface 7 --source-ip 192.168.60.54 --output-directory 'C:\private\bf6-test' --game-pid 8456 --above-normal
```

Путь, адрес и индексы — примеры этой машины. Для выключенного TUN добавить `--without-controller`: CPU и пробы продолжают измеряться без Clash API. В новом скрипте `automatic` означает обычную маршрутизацию Windows; при выключенном TUN она тоже физическая. В старых агрегатах с включённым TUN этот режим назывался `tun`. При заданном секрете локального Clash API передать его через `DEVICE_SETUP_CLASH_SECRET`, не через аргументы командной строки.

После завершения:

```powershell
python .\experiments\analyze-tun-capture.py 'C:\private\bf6-test\divert-HHMMSS.jsonl' --tun 22 --physical 7 --game-port 54260 --game-port 56136 --output 'C:\private\bf6-test\analysis.json'
```

Параметр `--phases` принимает JSONL с ISO-полем `at` и меткой `phase`. Для отдельной статистики устойчивого фокуса передать `--focus-samples 'C:\private\bf6-test\match-HHMMSS.jsonl'`. При известном времени окончания матча `--focus-before` принимает ISO timestamp с часовым поясом и ограничивает только эту дополнительную статистику. Текущий PID игры в команде измерителя нужно заменить после каждого перезапуска. `--above-normal` повышает только приоритет измерителя. Сам анализатор ничего не меняет в сети. Для сравнения приоритетов временный диагностический скрипт менял только живой процесс TUN и восстанавливал исходный класс в `finally`; длительность каждой фазы сохранена в результатах.

Документация: [планирование Windows](https://learn.microsoft.com/en-us/windows/win32/procthread/scheduling), [WinDivert и флаги пассивного захвата](https://reqrypt.org/windivert-doc.html).
