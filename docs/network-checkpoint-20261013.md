# Сохранённое состояние сети — 13 октября 2026

**Историческая контрольная точка до установки автозапуска.** В тот же день схема переведена на постоянную установку: [актуальная инструкция](warp-wireguard-windows.md). Рабочие параметры и выводы диагностики ниже сохранены; прежний ручной запуск заменён задачей Windows и службой сервера.

Пользователь попросил сохранить прогресс и оставить текущую работающую схему: «Мне вот так как щас настроено нравится». Дальнейшие эксперименты остановлены. **WireGuard на сервере сохранять**, существующий VLESS не удалять и не перезапускать ради этой диагностики. Это контрольная точка, а не утверждение, что скачки Battlefield окончательно исправлены.

## Что сейчас используется

- Windows, v2rayN 7.24.9; активный профиль по последнему подтверждению — `Germany WG via WARP`, SOCKS `127.0.0.1:19506`.
- TUN включён. Фактический sing-box inbound проверен при сохранении: `stack=system`, `mtu=9000`, `auto_route=true`, `strict_route=false`.
- Системный прокси — `Set system proxy`, локальный порт 10808. Профиль маршрутизации — `device-setup-windows`.
- Политика: игры напрямую, заблокированные ресурсы через иностранный VPN. При включённом TUN «напрямую» всё ещё проходит через локальную обработку sing-box, но минует зарубежный прокси.
- Транспорт заблокированного трафика: локальный sing-box WireGuard → SOCKS UDP relay → usque/WARP → WireGuard сервера → иностранный выход. В проверках выход был в Германии, `138.124.114.237`.
- Выставленный ранее AboveNormal для sing-box сохранён. Временные эксперименты High закончены, исходные приоритеты восстановлены.
- Игровой режим Windows пользователь выключил для последнего теста; обратно в ходе сохранения не переключали.
- Официальное приложение WireGuard для Windows установлено, но тестовые native-туннели и их маршруты удалены. Рабочий SOCKS 19506 использует WireGuard внутри sing-box.
- Основной WARP SOCKS 19486 для альтернативного профиля `Germany via WARP` также сохранён.

Настройки v2rayN в интерфейсе меняет сам пользователь. При продолжении сначала сверить живое состояние: PID, индексы адаптеров и адреса могут измениться.

## Восстановление после перезапуска компьютера

Постоянные приватные данные находятся в `%USERPROFILE%\.device-setup\warp-wireguard`. Задача `DeviceSetup WARP WireGuard` запускается при входе в Windows. Проверка:

```powershell
Get-ScheduledTask -TaskName 'DeviceSetup WARP WireGuard'
Get-Content "$env:USERPROFILE\.device-setup\warp-wireguard\status.json"
```

`wireguard-trial` больше не нужен. Старые приватные данные оставлены как резервная копия, а четыре экспериментальных процесса заменены постоянным supervisor. Штатному запуску не нужен SSH. Ручное обслуживание описано в актуальной инструкции.

Основной WARP→VLESS имеет отдельный runtime `%LOCALAPPDATA%\DeviceSetup\warp-bridge` и ранее настроенный автозапуск. [Описание этой схемы](warp-windows.md). Приватные конфиги нельзя заменять обезличенными шаблонами из Git без переноса собственных параметров.

## Что установлено, а что осталось открытым

- В вечернем сравнении WARP улучшал RTT до тестового сервиса на VPN-сервере примерно с 231–234 до 114 мс. Это не измерение пинга Battlefield.
- Native WireGuard работал, но сам по себе не устранил скачки и не заменил правила выборочной маршрутизации.
- В Battlefield обнаружены большие локальные задержки Ethernet → TUN. Переключение на system и выключение игрового режима не дали подтверждённого полного исправления. В последней серии пользователь не следил за игровым индикатором — это не подтверждение улучшения или ухудшения.
- Искусственная 100% CPU-нагрузка без игры не воспроизвела большие задержки. Одного процента загрузки CPU недостаточно для диагноза.
- WPR отказал при работающей игре, но заработал после её закрытия. Причина отказа не установлена; защита игры не менялась.
- macOS не тестировалась. В `physical_proxy.py` подготовлен Darwin `IP_BOUND_IF`; проверка на реальном Mac ещё нужна.

Уточнение после обсуждения: **WireGuard поддерживает routing** через AllowedIPs и системные маршруты. Нельзя считать вариант системного WireGuard отвергнутым. Для политики по доменам/приложениям нужен дополнительный механизм выборочной маршрутизации. Динамические DNS/IP-маршруты — возможное направление, но оно пока не реализовано и требует учёта общих CDN-адресов, собственного DNS приложений и различий Windows/macOS. Ручные исключения адресов игровых серверов пользователь отверг.
