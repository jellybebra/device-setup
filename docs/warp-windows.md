# WARP перед VLESS в Windows

Проверено 13 октября 2026 года: v2rayN 7.24.9, Xray 26.3.27, usque 4.2.1.

Схема: приложение → v2rayN/TUN → VLESS через локальный SOCKS usque → MASQUE/WARP → сервер VLESS → интернет. WARP меняет путь до сервера, а конечный выход обеспечивает VLESS. Отдельный WARP на проверенной сети выдавал российскую геолокацию и не выполнял требование зарубежного выхода.

## Результаты

Измерения без Battlefield, на одном компьютере и одном подключении:

| Проверка | VLESS напрямую | WARP → VLESS |
| --- | ---: | ---: |
| Медиана времени TCP-соединения с сервером, 30 попыток | 151 мс | 100 мс |
| p95 времени соединения | 212 мс | 113 мс |
| Загрузка 10 МБ, три повторения | 19,8–21,8 Мбит/с | 37,9–39,9 Мбит/с |
| Медиана запроса Cloudflare trace, 8 попыток | 559 мс | 523 мс |
| Медиана запроса Google 204, 8 попыток | 621 мс | 547 мс |

Это время TCP-соединения, а не ICMP ping. Результаты относятся к моменту проверки; вечерняя нагрузка и маршруты могут измениться. Эти замеры не доказывают ускорение Battlefield, который использует другие назначения и правила маршрутизации.

Повторная проверка после установки помощника: медиана TCP-соединения 135 мс напрямую и 103 мс через WARP (12/12 успешных попыток для каждого пути). Скорость менялась: два попеременных теста дали 23,4–24,8 Мбит/с напрямую и 26,7–46,6 Мбит/с через WARP; отдельный запрос через WARP перед ними дал 20,8 Мбит/с. Постоянного выигрыша в каждом запросе эти результаты не гарантируют.

### Почему ping/tracert и v2rayN показывают разное

В текущем TUN явно исключён `92.246.139.113/32`. Поэтому `ping` и Windows `tracert` к этому адресу продолжают измерять прямой ICMP-путь через провайдера. Цепочка задаётся в Xray для проксируемых соединений; ICMP через неё не переносится.

В [v2rayN 7.24.9](https://github.com/2dust/v2rayN/blob/7.24.9/v2rayN/ServiceLib/Services/SpeedtestService.cs) Tcping проверяет подключение к адресу и порту профиля. Real delay создаёт отдельное прокси-ядро и обращается к тестовому URL; текущий URL — `https://www.google.com/generate_204`. [ConnectionHandler](https://github.com/2dust/v2rayN/blob/7.24.9/v2rayN/ServiceLib/Handler/ConnectionHandler.cs) делает два HTTP-запроса одним клиентом и берёт меньшую задержку. Это время до Google через выходной сервер с возможным повторным использованием соединения, а не ICMP RTT до сервера. Сгенерированные конфиги тестирования обоих профилей проверены: тест действительно использует соответствующий профиль целиком, несмотря на прямое правило Google в основном конфиге.

Сравнивать нужно несколько попеременных серий к одинаковым назначениям, включая медиану, p95, ошибки и загрузку. Единичное значение Real delay может быть лучше у любого из двух профилей.

Проверка близким к Real delay способом (curl, два запроса одним процессом, минимум из двух, восемь повторений каждого профиля) дала медианы 106 мс напрямую и 101 мс через WARP. Прямые результаты лежали в диапазоне 88–137 мс, через WARP — 99–107 мс. Это отдельный замер, а не запуск внутреннего теста v2rayN: реализация HTTP-клиента отличается.

Cloudflare trace через отдельный all-proxy профиль показал `loc=DE`. Через активный v2rayN и системный TUN запрос `https://chatgpt.com/cdn-cgi/trace` показал `loc=US`. Таким образом, проверенные назначения имеют зарубежный выход, но страна зависит от назначения. Поле `warp=off` на конечном сайте ожидаемо: сайт видит выход VLESS, а WARP находится перед ним. UDP проверен DNS-запросом через SOCKS UDP ASSOCIATE и VLESS.

## Компоненты

- [usque](https://github.com/Diniboy1123/usque) — сторонний MASQUE-клиент. Используется `l4-socks`, адрес только `127.0.0.1:19486`.
- [warp-bridge.py](../warp-bridge.py) — локальный UDP-релей `127.0.0.1:19489`, привязанный через Windows `IP_UNICAST_IF` к физическому интерфейсу. Это предотвращает попадание WARP обратно в TUN.
- Клиент обращается через релей к `endpoint_v4` аккаунта usque на UDP/443. На проверенном аккаунте это `162.159.198.2`.
- Супервизор перезапускает usque после завершения процесса, трёх неудачных проверок удалённого SOCKS CONNECT или смены физического IPv4/адаптера. Ethernet предпочтителен; если он недоступен, выбирается физический адаптер с маршрутом по умолчанию и минимальной метрикой.
- Проверка соединения выполняется каждые 15 секунд, адаптера — каждые 60 секунд. При старте и восстановлении возможна пауза. Фактический вход после перезагрузки Windows отдельно не проверялся.

Официальный Cloudflare WARP оставлен отключённым, его экспериментальные переопределения сняты. Супервизор не меняет маршруты Windows, DNS или настройки zapret.

## Установка

Нужны Python с `pythonw.exe`, проверенный Windows-бинарник usque и зарегистрированный аккаунт usque с исходным `endpoint_v4`. Аккаунт содержит секретные ключи: хранить его вне репозитория.

Из корня репозитория:

```powershell
.\install-warp-bridge.ps1 -UsquePath 'C:\path\usque.exe' -AccountPath 'C:\private\usque-account.json'
```

Установщик копирует исполняемые файлы и приватный аккаунт в `%LOCALAPPDATA%\DeviceSetup\warp-bridge`, создаёт `Start WARP.lnk`, `Stop WARP.ps1` и ярлык `DeviceSetup WARP.lnk` в пользовательской папке автозагрузки. Администраторские права для помощника не нужны. Порты 19486/TCP и 19489/UDP должны быть свободны; сторонний процесс на этих портах не завершается автоматически.

Для первого запуска открыть `Start WARP.lnk`. Дублирующий запуск завершается благодаря именованному mutex. Логи находятся в `bridge.log` и `usque.log`. Код работает из установленной папки и не зависит от существования Git worktree.

При установке проверены: обычная остановка и запуск тем же ярлыком, запрет второго экземпляра, автоматический перезапуск после принудительного завершения дочернего usque, HTTPS через основной TUN и UDP через тестовый VLESS-профиль. Смена физического адаптера и перезагрузка Windows вживую не проверялись.

## v2rayN

1. Configuration → Add [SOCKS]: Remarks `WARP-local`, Address `127.0.0.1`, Port `19486`, без имени пользователя и пароля.
2. Configuration → Add Proxy Chain: Remarks `Germany via WARP`, Core Type `Xray`.
3. В таблице дочерних профилей через контекстное меню Add Child добавить сначала `WARP-local`, затем существующий немецкий VLESS-профиль. Порядок сверху вниз именно такой.
4. Confirm, затем Set as active для `Germany via WARP`. Enable TUN остаётся включённым.

Генерируемый Xray outbound `proxy` должен иметь `streamSettings.sockopt.dialerProxy`, указывающий на SOCKS outbound `127.0.0.1:19486`.

Существующий профиль маршрутизации Windows остаётся активным. Google/YouTube, Discord и другие прямые исключения продолжают идти напрямую через zapret; заблокированные сайты и явно проксируемые назначения — через цепочку. Это не режим «весь интернет за границей». Для такого режима потребуется отдельно изменить routing с учётом локальных адресов и исключений.

Проверка активного TUN без явно заданного HTTP/SOCKS-прокси:

```powershell
curl.exe --noproxy '*' --ssl-revoke-best-effort --max-time 15 https://chatgpt.com/cdn-cgi/trace
```

Ожидается зарубежный `loc`. `--ssl-revoke-best-effort` разрешает недоступность сервера проверки отзыва в Windows, сохраняя проверку сертификата TLS.

## Возврат и удаление автозапуска

Для быстрого возврата: Set as active на прежнем немецком VLESS-профиле. После этого можно запустить `Stop WARP.ps1` в установленной папке. Сам профиль `WARP-local` отдельно активировать не нужно: его выход может иметь российскую геолокацию.

Для отключения будущего автозапуска удалить только ярлык `DeviceSetup WARP.lnk` из `shell:startup`. Для полного удаления сначала выбрать прежний профиль, остановить помощника и удалить созданные WARP-профили в v2rayN; затем можно удалить установленную папку. Существующие VLESS-профили и официальный Cloudflare WARP остаются независимыми.

## Сравнение с WireGuard, 13 октября 2026

На `test` добавлен изолированный интерфейс `wg-codex`, UDP/51871, сеть `10.203.13.0/29`, MTU 1200. Для одновременного сравнения использовались разные ключи и адреса прямого клиента и клиента через WARP. Серверный WireGuard работает в ядре Linux; клиент — userspace endpoint sing-box 1.13.12 с локальным SOCKS. Существующий VLESS-контейнер и его конфигурация не менялись и не перезапускались. Установлен только небольшой пакет `wireguard-tools`; новые правила forwarding/NAT ограничены тестовым интерфейсом и подсетью.

WARP → WireGuard требует UDP, поэтому используется второй аккаунт и режим `usque socks`, с пользовательским сетевым стеком. Прямой SOCKS detour sing-box не заработал: usque 4.2.1 отвергал UDP ASSOCIATE с нулевым адресом/портом. [Локальный релей](../experiments/socks-udp-relay.py) явно объявляет реальный UDP-порт и переносит зашифрованные WireGuard-пакеты. Итого клиентская схема: sing-box WireGuard → UDP-релей → usque socks → физический MASQUE-релей → Cloudflare → сервер WireGuard. Это сравнение конкретных реализаций; оно не доказывает превосходство протокола WireGuard во всех конфигурациях.

[Скрипт сравнения](../experiments/compare-proxies.py) менял порядок профилей в каждом раунде. Для каждого профиля: 40 UDP DNS-запросов к 8.8.8.8; шесть раундов запросов к Google 204 и Cloudflare trace, по два запроса одним curl-процессом; три загрузки одного файла 10 МБ. CPU компьютера во время проверки был около 4%.

| Вариант | HTTPS с новым соединением, медиана | Минимум из двух HTTPS-запросов, медиана | Загрузка, медиана |
| --- | ---: | ---: | ---: |
| VLESS | 528 мс | 122 мс | 27,79 Мбит/с |
| WARP → VLESS | 519 мс | 101 мс | 30,92 Мбит/с |
| WireGuard напрямую | 829 мс | 271 мс | 15,72 Мбит/с |
| WARP → WireGuard | 315 мс | 101 мс | 37,45 Мбит/с |

Во всех проверках получены успешные ответы. В первой серии UDP у WARP → WireGuard были более заметные всплески (p95 190 мс против 115 мс у WARP → VLESS). Дополнительная попеременная серия из 100 запросов на каждый WARP-вариант дала:

| Вариант | UDP медиана | p95 | Максимум | Нет ответа |
| --- | ---: | ---: | ---: | ---: |
| WARP → VLESS | 95,16 мс | 103,04 мс | 420,33 мс | 0/100 |
| WARP → WireGuard | 96,88 мс | 105,17 мс | 116,81 мс | 0/100 |

Устойчивого преимущества по UDP-задержке не обнаружено. Основной выигрыш WireGuard в этом тесте — новые HTTPS-соединения и загрузка; прямой WireGuard сейчас работает, но заметно медленнее. Параллельная работа двух WARP-клиентов и небольшой размер загрузок ограничивают переносимость результата на другие условия.

WireGuard выходит с `138.124.114.237`, страна DE, включая ChatGPT. Существующая серверная маршрутизация VLESS отправляет OpenAI через отдельный US-выход и к WireGuard не применяется. `api.openai.com/v1/models` без токена в обоих случаях вернул ожидаемый HTTP 401 (Missing bearer authentication), а не региональный отказ. Вход в аккаунт ChatGPT и все функции сервиса этим не проверены.

### Попробовать в v2rayN

Оставлен отдельный экспериментальный SOCKS `127.0.0.1:19506`. Configuration → Add [SOCKS]: Alias `Germany WG via WARP`, Address `127.0.0.1`, Port `19506`, без логина/пароля. Этот профиль уже содержит всю цепочку; добавлять перед ним WARP-local или после него VLESS не нужно. После Set as active сохраняются текущий TUN и правила маршрутизации Windows.

Для возврата выбрать `Germany via WARP`. У тестового режима **нет автозапуска Windows**; автозапуск основного WARP → VLESS остаётся независимым. Файлы, ключи и копии релеев хранятся вне Git в `%LOCALAPPDATA%\DeviceSetup\warp-latency-20261013`. Там находится `wireguard-trial.ps1` с действиями `Start`, `Stop`, `Status` и ярлыки запуска/остановки. Start проверяет свободные порты и поднимает только отдельный WireGuard-интерфейс на сервере, если тот отсутствует. Экспериментальный запуск рассчитан на физический адаптер Ethernet.

[Менеджер эксперимента](../experiments/wireguard-trial.ps1) проверяет PID, путь и время создания перед остановкой собственных процессов. Stop завершает только локальные компоненты кандидата. Для удаления серверного интерфейса и его правил выполнить:

```powershell
ssh test 'bash /opt/warp-wireguard-test/wireguard-server.sh down'
```

Это сохраняет ключи в `/opt/warp-wireguard-test`, поэтому эксперимент можно повторить командой `up`; рабочий VLESS не затрагивается. Состояние интерфейса и iptables не добавлялось в загрузку сервера. [Серверный скрипт](../experiments/wireguard-server.sh) предназначен именно для проверенного сервера с `ens3` и указанными адресами.

### Воспроизведение и исходные измерения

Исходные ответы и времена сохранены в [experiments/results/2026-10-13](../experiments/results/2026-10-13). Файлы содержат результаты измерений и публичные выходные IP; аккаунты usque, UUID VLESS и приватные ключи WireGuard туда не входят.

Все команды ниже — для первоначальной подготовки отдельного эксперимента, а не для повторной установки поверх работающего. Нужны Python, OpenSSH, usque 4.2.1, Xray и sing-box из v2rayN. Сначала проверить свободные порты 19482, 19487, 19501–19507 на клиенте и UDP/51871 на сервере. Основной WARP SOCKS 19486 должен работать. Для UDP-экземпляра usque использовать отдельный зарегистрированный аккаунт.

На сервере установить `wireguard-tools` без дополнительных рекомендуемых пакетов. Загрузить `experiments/wireguard-server.sh` через SCP во временный файл, выполнить `bash ... up` и сохранить копию скрипта в `/opt/warp-wireguard-test/wireguard-server.sh`. Скрипт проверяет порт, тестовую сеть, интерфейс и цепочку firewall, создаёт ключи с правами только для владельца. Выгрузить `client-export.json` через SCP в приватную папку клиента под именем `wireguard-peers.json`.

Генератор использует реальную конфигурацию VLESS, поэтому перед копированием `binConfigs/config.json` должен быть выбран VLESS или цепочка с конечным VLESS. Копию хранить вне репозитория. Подготовить конфиги в новой приватной папке:

```powershell
python .\experiments\prepare-comparison.py --vless-runtime 'C:\private\vless-runtime.json' --wireguard-peers 'C:\private\wireguard-peers.json' --usque-account 'C:\private\usque-udp-account.json' --output 'C:\private\wg-trial'
Copy-Item .\experiments\physical_proxy.py,.\experiments\socks-udp-relay.py,.\experiments\wireguard-trial.ps1 'C:\private\wg-trial'
.\experiments\wireguard-trial.ps1 -DataDirectory 'C:\private\wg-trial' -Action Start
```

Генератор отказывается писать секреты внутрь checkout и перезаписывать существующие конфиги. Менеджер рассчитан на SSH-алиас `test`, адаптер `Ethernet`, текущие пути установки v2rayN/usque и проверенный адрес Cloudflare. На другом компьютере эти параметры нужно сверить перед запуском.

Для полного сравнения отдельно запустить Xray с `vless-direct.json` и `vless-warp-l4.json`, а sing-box — с `wireguard-direct.json`; у каждого свой локальный порт. Запускать из отдельных терминалов, используя `xray.exe run -config <файл>` и `sing-box.exe run -c <файл>`. Затем:

```powershell
python .\experiments\compare-proxies.py 'C:\private\wg-trial\comparison.json'
```

После сравнения завершить эти три измерительных процесса. `wireguard-trial.ps1 -Action Stop` останавливает только четыре собственных компонента WARP → WireGuard; основной WARP → VLESS остаётся независимым.
