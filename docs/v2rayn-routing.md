## Доменные правила и HTTP/3

В обоих шаблонах Xray в `sniffing.destOverride` включены `http`, `tls` и `quic`. Это позволяет применять доменные правила к HTTP/3, когда TUN передаёт Xray соединение с IP-адресом назначения. Без `quic` запросы браузера по UDP могут попасть в правило «Остальное напрямую», хотя обычный HTTPS-запрос через TCP идёт через прокси. См. [документацию Xray по sniffing](https://xtls.github.io/en/config/inbound.html#sniffingobject).

Проверка HTTP 200 через `curl` подтверждает только конкретный запрос, а не загрузку приложения в браузере. При региональном редиректе проверяй также поведение браузера после Reload.

## Cloudflare Tunnel: когда нужны исключения

Cloudflare Tunnel работает через VLESS как с TLS, так и с REALITY.
Нужна доступность **TCP/7844 для HTTP/2** или **UDP/7844 для QUIC**.
В наших профилях правило `7844 → proxy` в Routing Setting и шаблоне Xray
задаёт нужный выход при раздельной маршрутизации; в режиме, где весь трафик
уже идёт через прокси, отдельное правило избыточно. Системный HTTP-прокси
сам по себе не подтверждает, что транспорт туннеля проходит через VPN:
проверяй TUN и фактический маршрут соединений.

Исключения `h2.cftunnel.com`, `quic.cftunnel.com`, `probe.cftunnel.com` решают
другую задачу. Cloudflared выбирает IP сервера через discovery и использует
эти имена как SNI: соответственно для HTTP/2, QUIC и предварительной проверки.
Если Xray со сниффингом и `routeOnly: false` подменяет выбранный IP на SNI,
он может попытаться подключиться к имени, у которого нет адресной DNS-записи.
13 октября 2026 года эти три имени не разрешались в IP как на Mac, так и на
нашем сервере. Это не требование к TLS-сертификату VLESS и не особенность REALITY.

| Сниффинг на конкретном узле Xray | Нужны исключения Cloudflare |
| --- | --- |
| Выключен | Нет |
| Включён, `routeOnly: true` | Нет: домен используется только для маршрутизации |
| Включён, `routeOnly: false` (также значение по умолчанию) | Да, если соответствующий TLS/QUIC-протокол входит в `destOverride` |

Условие нужно проверить **отдельно на клиенте и сервере**. Смена VLESS-сервера
в v2rayN не удаляет клиентские исключения. На нашем сервере при проверке
были включены HTTP/TLS-sniffing и три исключения; `routeOnly` отсутствовал,
то есть использовалось `false`. Серверный список не включал `quic`, поэтому
именно серверное исключение `quic.cftunnel.com` там было запасом на будущее.

### Проверка 13 октября 2026 года

Версии: macOS, Xray **26.3.27**, cloudflared **2026.9.1**; Xray нашего сервера
**26.6.1**. Проверены актуальные версии репозиториев `device-setup` (`3844158`)
и `vless-docker` (`2c75d9d`). Рабочий v2rayN и серверные настройки не менялись.

В текущем TUN с активным сторонним VLESS/TLS-прокси успешно прошли обычные
запуски с `--protocol http2`, `--protocol quic` и `--protocol auto`:
зарегистрирован туннель, публичный HTTPS-запрос вернул HTTP 200 и контрольное
тело локального сервера. Повторная серия подтвердила результат; `auto`
зарегистрировал соединение через QUIC.

Для сравнения клиентских режимов запускались отдельные Xray на свободных
loopback-портах, с единственным выходом на выбранный VLESS-сервер. Тестовый
TCP-переходник передавал соединение cloudflared в SOCKS Xray с исходным IP
Cloudflare (`198.41.200.13:7844`); TLS оставался сквозным. Этот адрес был
фиксирован только для эксперимента, его не нужно прописывать в рабочие настройки.

| Клиентский режим | Сторонний VLESS/TLS | Наш VLESS/REALITY |
| --- | --- | --- |
| Сниффинг выключен, исключений нет | HTTP/2: работает | HTTP/2: работает |
| Подмена назначения + три исключения | HTTP/2: работает | HTTP/2: работает |
| `routeOnly: true`, исключений нет | HTTP/2: работает | HTTP/2: работает |
| Подмена назначения, исключений нет | HTTP/2: не подключается | HTTP/2: не подключается |

«Работает» здесь означает регистрацию туннеля и получение контрольного ответа
через публичный URL. В неуспешном режиме лог Xray показывал отправку
`tcp:h2.cftunnel.com:7844` вместо исходного IP, cloudflared — ошибку TLS.
Для проверки публичных URL в изолированной серии использовался адрес,
полученный через Cloudflare DoH: системный DNS иногда не разрешал только что
выданное имя. Проверка сертификата HTTPS оставалась включённой.

Ограничения: настройки стороннего сервера не читались, поэтому по успешному
тесту нельзя определить, выключен ли там сниффинг, включён ли `routeOnly`
или используются исключения. Серверные исключения нашего сервера не снимались.
QUIC в опытах с фиксированным edge давал тайм-аут даже с исключениями,
включая контроль через рабочий TUN. Этот результат не отделяет влияние
сниффинга от остальных условий и не используется как доказательство его влияния
на QUIC. Проверка не измеряет длительную стабильность или производительность.

### Что оставить в рабочей настройке

Для текущих шаблонов с `routeOnly: false` **оставь точечные исключения**.
Они устраняют воспроизводимый сбой и не требуют менять маршрутизацию остальных
приложений. Если нужен общий переход к сохранению исходных IP, альтернативой
будет `routeOnly: true` без исключений; сначала нужно проверить DNS и остальные
доменные маршруты. Глобальное отключение сниффинга лишит профиль части
доменных правил для соединений, поступающих как IP.

У cloudflared обычно можно оставить `--protocol auto`: он начинает с QUIC
и допускает переход на HTTP/2. Принудительный `http2` нужен как обход проблем
UDP, а не как обязательное условие работы через VLESS. Сниффинг с подменой
SNI этот флаг не исправляет. Преимущество по скорости между вариантами
в этой проверке не измерялось.

Источники: [порты и адреса Cloudflare Tunnel](https://developers.cloudflare.com/cloudflare-one/networks/connectors/cloudflare-tunnel/configure-tunnels/tunnel-with-firewall/),
[SNI и выбор протокола в cloudflared 2026.9.1](https://github.com/cloudflare/cloudflared/blob/2026.9.1/connection/protocol.go),
[семантика sniffing и routeOnly в Xray](https://xtls.github.io/en/config/inbound.html#sniffingobject).



## Настройка компьютера

1. Скачай v2rayN из [официального релиза](https://github.com/2dust/v2rayN/releases/tag/7.24.9).

   - Windows — `v2rayN-windows-64.zip`.
   - Mac с Apple Silicon — `v2rayN-macos-arm64.dmg`.
   - Mac с Intel — `v2rayN-macos-64.dmg`.

2. Запусти приложение.

   - Windows — распакуй архив и запусти `v2rayN.exe` от администратора.
   - Mac — перенеси приложение в «Программы» и открой его.

3. Добавь VPN-сервер.

   - Скопируй свою подписку или ссылку `vless://…`.
   - Выбери **Configuration / Серверы → Import Share Links from clipboard / Импорт ссылок общего доступа из буфера обмена**.
   - Для подписки открой **Subscription Group / Группа подписки → Update current subscription without proxy / Обновить текущую подписку без прокси**. Если подписка доступна только через VPN, выбери **Update current subscription with proxy / Обновить текущую подписку через прокси**.
   - Нажми правой кнопкой на нужный сервер и выбери **Set as active / Сделать активным**.

4. Настрой Geo-файлы.

   - Открой **Settings / Настройки → Option Setting / Параметры → v2rayN settings / Настройки v2rayN**.
   - В поле **Geo files source (optional) / Источник файлов Geo (необязательно)** укажи:

     ```text
     https://github.com/runetfreedom/russia-v2ray-rules-dat/releases/latest/download/{0}.dat
     ```

   - Сохрани настройки кнопкой **Confirm / Подтвердить**.
   - Открой **Help / Помощь → Check Update / Обновить**. Оставь отмеченным только **GeoFiles**, затем нажми **Check Update / Обновить**.

5. Скопируй готовый шаблон.

   - Открой **Шаблон Xray** для своей системы из таблицы выше.
   - Нажми **Raw** на GitHub.
   - Скопируй весь JSON.

6. Включи шаблон Xray.

   - Открой **Settings / Настройки → Full Config Template Setting / Настройка полного шаблона конфигурации → v2ray Full Config Template / Полный шаблон конфигурации v2ray**.
   - Включи **Enable Full Config Template / Включить полный шаблон конфигурации**.
   - Вставь одинаковый JSON в оба поля:
     - **xray config template json**.
     - **xray tun config template json**.
   - Сохрани настройки кнопкой **Confirm / Подтвердить**.

7. Настрой TUN.

   - Открой **Settings / Настройки → Option Setting / Параметры → Tun Mode settings / Настройки режима TUN**.
   - **Strict Route / Строгая маршрутизация** — выключено.

8. Исключи VPN-сервер из TUN.

   - В тех же настройках найди **Route Exclude Address / Адреса, исключаемые из маршрутизации**.
   - Добавь IP своего VPN-сервера. Ниже адрес для примера — замени его своим:

     ```text
     203.0.113.10/32
     ```

   - При смене сервера укажи его IP:
     - `/32` для IPv4.
     - `/128` для IPv6.
   - Сохрани настройки кнопкой **Confirm / Подтвердить**.

9. Импортируй правила для TUN.

   - Открой **Правила Routing Setting** для той же системы из таблицы выше, нажми **Raw** и скопируй JSON.
   - Открой **Settings / Настройки → Routing Setting / Настройки маршрутизации**. Создай отдельный профиль с названием `device-setup-windows` или `device-setup-macos`.
   - В редакторе профиля импортируй правила из буфера обмена, сохрани и выбери этот профиль активным. При повторном импорте замени прежний список целиком, чтобы не оставить старые правила выше новых.
   - В режиме TUN sing-box использует этот профиль перед передачей трафика Xray. Правила процессов (`Discord.exe` в Windows, `Discord` и его вспомогательные процессы в macOS) покрывают в том числе голосовые соединения без домена.

10. Включи защищённый DNS для TUN.

   - В **Settings / Настройки → DNS settings** полностью замени содержимое **Domestic DNS** и **Remote DNS** на `https://1.1.1.1/dns-query`; **Bootstrap DNS** — на `1.1.1.1`.
   - При включённом TUN обычные DNS-запросы идут через HTTPS даже для `direct`: это обход прокси, а не отключение шифрования DNS. Без TUN отдельно настрой защищённый DNS в системе.

11. Включи VPN.

   - Нажми **Reload / Перезапустить службу**.
   - Включи **Enable Tun / Включить TUN**.
   - Если TUN уже включён, выключи и снова включи **Enable Tun / Включить TUN**.

## Instagram, X и Telegram через Zapret Local на macOS

Для уже настроенного профиля с Discord через локальный SOCKS Zapret:

```sh
python3 update-v2rayn-zapret.py --check
python3 update-v2rayn-zapret.py
```

После выполнения нажми **Reload** в v2rayN. Скрипт находит локальный выход по
существующему правилу Discord и проверяет SOCKS-порт, добавляет семь правил
в начало активного профиля, сохраняя остальные правила и выбранный VPN.
Полные шаблоны конфигурации должны быть отключены: они обходят Routing Setting.
Скрипт проверяет конфигурацию установленным Xray, делает SQLite backup и не
перезапускает приложения. Повторный запуск не дублирует правила.
Резервные копии лежат в `~/Library/Application Support/v2rayN-backups/`.

[Дополнительные правила](../configs/v2rayn/macos/zapret/social-routes.json)
охватывают Instagram и его CDN, X/Twitter и медиа, домены Telegram,
[официальные IPv4-сети Telegram](https://core.telegram.org/resources/cidr.txt)
и процессы Telegram в TUN. `fbcdn.net` используется как общий CDN Meta:
это правило может затронуть также ресурсы Facebook. Категории доменов берутся
из установленного `geosite.dat`. Отдельно выбраны Instagram, Twitter и Telegram,
без перевода всего Meta или остальных сервисов в Zapret.

Instagram и X используют проверенный TCP-путь: дополнительные правила
блокируют только UDP/443 этих сервисов, чтобы браузер переходил с QUIC на TCP.
В Zapret Local для Instagram и медиа X включён `multidisorder`; самому x.com
выделен fake-профиль с 12 повторами. Для `abs.twimg.com` и `pbs.twimg.com`
DNS использует `twimg.twitter.map.fastly.net`, для `video.twimg.com` —
`dualstack.video.twitter.map.fastly.net`: на другом CDN наблюдались обрывы
загрузок после первых 15 КБ. Исходные URL, SNI и проверка TLS сохраняются.
При ошибке DNS/TCP по имени помощник пробует
Google DoH с альтернативным CDN-регионом (`edns_client_subnet=8.8.8.0/24`).
Запрос идёт через тот же физический интерфейс; IP пользователя не отправляется
в ECS, конкретные адреса CDN не закрепляются. Это не переключение на VPN.
Для недоступных региональных медиасерверов `scontent-*.cdninstagram.com`,
`scontent-*.xx.fbcdn.net` и `video-*.xx.fbcdn.net` резервный DNS-запрос использует
глобальный адрес соответствующего CDN. Исходные URL, SNI и проверка TLS
остаются прежними. Это необходимо для аватаров и видео: проверка только HTML,
CSS и JS не подтверждает доступность регионального медиасервера.

Telegram Desktop использует [встроенный локальный MTProto-мост](../apps/zapret-local/telegram/README.md)
на базе Flowseal/tg-ws-proxy, включённый в `.app` и DMG: одних правил для заблокированных TCP-адресов DC
недостаточно. У него включён WebSocket и резерв CF, все исходящие соединения
направлены через SOCKS Zapret. В Desktop выбран `127.0.0.1:49950`, отображается
`online`. Проверены корректные ответы MTProto для DC1–5 и DC203. Правила
v2rayN для Telegram сами по себе не заменяют настройку этого моста и не
гарантируют работу Telegram Web, `t.me` или звонков.
