# Постоянный WARP → WireGuard в Windows

**Архивная клиентская схема.** 15 октября 2026 выполнен переход на
[Clash Verge / Mihomo](mihomo-windows-trial.md). Описанные ниже задачи v2rayN
и supervisor отключены; их файлы оставлены для отката. Не включать старый TUN
одновременно с TUN Clash. Сервер сейчас работает в wg-easy с MTU 1420.

Рабочий профиль v2rayN `Germany WG via WARP` использует локальный SOCKS `127.0.0.1:19506`. Транспорт запускается автоматически при входе пользователя в Windows; команды `wireguard-trial` для обычного использования не нужны. Отдельный системный WireGuard Windows в этой схеме не используется: WireGuard обслуживает выделенный sing-box.

## Устройство

Задача планировщика **DeviceSetup WARP WireGuard** запускает `pythonw.exe` без консольного окна с `warp-wireguard.py`. Постоянная папка — `%USERPROFILE%\.device-setup\warp-wireguard`; права ограничены текущим пользователем, администраторами и SYSTEM. Там находятся копии `usque.exe`, `sing-box.exe`, вспомогательных модулей и приватные конфиги. Для работы не нужен Git worktree, папка эксперимента или SSH с компьютера на сервер.

Папка выбрана вне AppData: при установке из текущего окружения файлы AppData были видны установщику, но отсутствовали для задачи планировщика. Запуск из `.device-setup` проверен самим планировщиком. JSON записывается в UTF-8 без BOM, включая установку через Windows PowerShell 5.1: usque отвергает BOM.

Внешние UDP-сокеты WARP привязаны к физическому интерфейсу, чтобы TUN не захватил собственный транспорт. Приоритетный адаптер — Ethernet; если он недоступен, выбирается другой подключённый физический адаптер с IPv4 и маршрутом по умолчанию. VPN-адаптеры исключены из выбора.

Локальные порты: WARP SOCKS 19501, физический UDP relay 19502, WireGuard UDP relay 19505, конечный SOCKS 19506. Все слушатели привязаны к loopback. Совместимость с UDP ASSOCIATE usque сохранена из проверенной цепочки. Игровые маршруты и настройки v2rayN supervisor не меняет.

### Проверка без WireGuard UDP relay, 15 октября 2026

На установленных sing-box 1.13.12 и usque 4.2.1 проверен прямой `detour: warp-udp`
у WireGuard endpoint с адресом сервера `92.246.139.113:51871`. Использовались
отдельный свободный SOCKS-порт 19606 и неактивный peer `10.203.13.5`; рабочий
клиент `.2`, его процессы и конфигурация не менялись. Физический relay 19502
сохранялся в обоих вариантах, чтобы WARP не попадал обратно в TUN.

Без relay HTTPS не прошёл (ошибка разрешения DNS через туннель), UDP DNS — 0/5.
При возвращении relay на тестовый порт 19605 тот же клиент получил HTTPS-ответ
с выходом `138.124.114.237` и UDP DNS 5/5, около 98–107 мс.

Отдельная проверка SOCKS показала: usque отвечает успехом на UDP ASSOCIATE
с адресом `0.0.0.0:0`, но затем отбрасывает пакеты с сообщением
`udp address 127.0.0.1:… is not associated with tcp`. Если объявить фактический
локальный UDP-адрес и порт, DNS-ответ приходит. Это несовместимость обработки
UDP ASSOCIATE; HTTP/UDP-доступность через WARP при корректной ассоциации сохранена.

На момент проверки [последний опубликованный usque — 4.2.1](https://github.com/Diniboy1123/usque/releases/tag/v4.2.1),
то есть установленная версия. Relay 19505 оставлен в рабочей цепочке.
Тестовые процессы завершены. Ускорение от удаления relay не измерено:
вариант без него не установил рабочее соединение.

Встроенный контроль раз в 15 секунд проверяет SOCKS CONNECT через всю цепочку; три неудачи подряд вызывают переподключение. Изменение физического интерфейса/IP проверяется раз в минуту. Если сети ещё нет при входе в Windows, supervisor ждёт её с повторными попытками. Аварийный выход любого дочернего процесса перезапускает цепочку. Windows Job Object завершает дочерние процессы при аварии supervisor; планировщик повторяет запуск через минуту. Повторные экземпляры запрещены задачей и mutex.

Логи ротируются: до 2 МБ на файл и две резервные копии для supervisor, usque и sing-box. Уровень sing-box — warn, без постоянного журнала каждого посещённого адреса. `status.json` показывает состояние `connecting`, `healthy`, `reconnecting` или `stopped`; состояние healthy означает последнюю успешную проверку соединения, а не гарантию доступности всех сайтов.

## Установка и обслуживание

Установщик запускается в административном PowerShell с существующими приватными конфигами. Он копирует бинарники и настройки и регистрирует задачу; старую цепочку автоматически не убивает и задачу сразу не запускает. Перед первым стартом остановить только принадлежащие старой установке процессы, проверив их путь и время создания. Секреты в аргументах не передаются, только пути файлов.

```powershell
.\install-warp-wireguard.ps1 -AccountPath 'C:\private\account.json' -WireGuardConfigPath 'C:\private\wireguard.json' -UsquePath 'C:\tools\usque.exe' -SingBoxPath 'C:\tools\sing-box.exe'
Start-ScheduledTask -TaskName 'DeviceSetup WARP WireGuard'
```

Для проверки:

```powershell
Get-ScheduledTask -TaskName 'DeviceSetup WARP WireGuard'
Get-Content "$env:USERPROFILE\.device-setup\warp-wireguard\status.json"
curl.exe --proxy socks5h://127.0.0.1:19506 https://www.cloudflare.com/cdn-cgi/trace
```

При необходимости ручного перезапуска из административного PowerShell:

```powershell
Stop-ScheduledTask -TaskName 'DeviceSetup WARP WireGuard'
Start-ScheduledTask -TaskName 'DeviceSetup WARP WireGuard'
```

Остановка задачи временно лишает активный профиль v2rayN VPN-выхода. Для штатной остановки можно создать пустой `stop.request` в постоянной папке; при следующем старте этот файл удаляется. Для обновления бинарников сначала остановить задачу, сохранить старые файлы, проверить новую версию и снова запустить. Установщик намеренно отказывается перезаписывать существующую установку без проверки.

v2rayN запускается собственной существующей задачей автозапуска. В его сохранённых настройках остаются активный `Germany WG via WARP`, включённый TUN system и текущая маршрутизация. Если интернет при входе появляется не сразу, заблокированные ресурсы станут доступны после установления WARP; ручной старт транспорта не требуется. Сам v2rayN остаётся в своей установленной папке — её удаление или перенос требует перенастройки его собственного автозапуска.

## Сервер

С 15 октября 2026 сервер работает через **wg-easy 15.4.0** в отдельном
Compose-проекте `wireguard`, каталог `/opt/wireguard`. Панель —
[wg.vzl0m.com](https://wg.vzl0m.com), штатный вход wg-easy.
Конфигурация и инструкция — [vless-docker/wireguard](https://github.com/jellybebra/vless-docker/tree/master/wireguard).
Ключи четырёх клиентов, UDP 51871, подсеть `10.203.13.0/29` и выход
`138.124.114.237` сохранены; интерфейс `wg0` находится внутри контейнера.
Доступ VPN-клиентов к частным сетям блокируется firewall контейнера.

```sh
docker inspect -f '{{.State.Health.Status}}' wireguard-wg-easy-1
docker exec wireguard-wg-easy-1 wg show wg0 latest-handshakes
```

Старый `device-setup-wireguard.service` отключён. Его конфигурация и скрипт отката
сохранены в `/opt/codex-backups/wireguard-20261015/`. Не запускать старую службу
или `install-wireguard-service.sh` одновременно с wg-easy: они используют один
UDP-порт. При миграции VLESS не перезапускался.

## Ограничения проверок

Проверено 13 октября 2026, около 21:19 МСК:

- Задача Windows работает с триггером входа пользователя; собственный автозапуск v2rayN включён.
- Принудительное завершение дочернего usque автоматически восстановило всю цепочку. Остановка задачи завершила supervisor и оба дочерних процесса; повторный запуск задачи вернул состояние healthy.
- После обоих тестов HTTPS через SOCKS 19506: выход `138.124.114.237`, `loc=DE`. Через v2rayN 10808 OpenAI models без токена отвечает ожидаемым HTTP 401, Google generate_204 — HTTP 204. Это проверка доступности, не входа в аккаунт ChatGPT.
- TUN сохранился включённым, stack system, MTU 9000, strict_route false. Маршруты игр не менялись.
- Серверная служба enabled/active, четыре peer сохранены. Контролируемый перезапуск службы не дублировал правила firewall и не перезапустил VLESS: время старта контейнера осталось `2026-10-04T07:56:33.425804756Z`.

Сохранение этой схемы выбрано пользователем. Диагностика Battlefield не доказала полного устранения скачков TUN; это отдельный вопрос, описанный в [отчёте](battlefield-latency-20261013.md). Настройка macOS не выполнялась. Контролируемый перезапуск процессов проверяет восстановление, но не заменяет фактическую перезагрузку всего компьютера или сервера.
