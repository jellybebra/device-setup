# Huawei AX3: VLESS, прямой YouTube и голос Discord

Настроено на Huawei WS7100-20 VER.A, debug 10.0.5.26, Linux 4.4.197 ARMv7.
Keenetic не изменялся. Huawei LAN: 192.168.3.1. Правила распространяются
на проводные и Wi-Fi устройства Huawei: мосты br0/br1, основную сеть
192.168.3.0/24 и гостевую 192.168.155.0/24. Устройства непосредственно
на Keenetic не затрагиваются.

## Итоговая маршрутизация

- YouTube, googlevideo и связанные домены из списков Windows Zapret:
  напрямую через локальный tpws с разделением TLS-запроса.
- Discord: сайт, API и служебные TCP-соединения через выбранный VLESS.
- Голос Discord: UDP-порты 19294–19344 и 50000–50100 напрямую,
  диапазоны взяты из пользовательского general (EXP).bat.
  Исключение действует по порту: другой UDP на тех же портах также прямой.
- Остальные TCP/UDP соединения классифицирует Xray по перенесённым правилам
  v2rayN: Steam, Telegram, Claude, ChatGPT, ru-blocked, private и др.
  Весь UDP больше не направляется принудительно в VLESS.
- Локальные, служебные и multicast-адреса обходят перехват.
- UDP/443 отклоняется, чтобы браузеры быстро переходили с QUIC на TCP.
  Это нужно для прямого YouTube через tpws, который работает только с TCP.

Это не точная копия Zapret EXP: в ядре Huawei отсутствует NFQUEUE.
Используется tpws v72.13 из официального Zapret. Полный прямой Discord
через tpws оказался ненадёжным: большие HTTP-ответы обрывались около 15 КБ,
поэтому его TCP оставлен через VLESS, а голос — напрямую ради низкого пинга.
Процессные правила Windows на роутере недоступны. IPv6 не проксируется;
во время проверки глобального IPv6 на LAN не было.

## Автозапуск

После перезагрузки Huawei ничего на ПК запускать не требуется.
Выбранный профиль и флаг включения хранятся в /data/mvp.

Штатный mic подключает /patch/etc поверх /etc через OverlayFS.
Добавлен только /patch/etc/rc.d/S99mvp; исходный rootfs не изменён.
Он запускает /data/mvp/boot.sh, затем mvp-service.sh watch.
Watchdog запускает Xray, hev-socks5-tunnel и tpws, восстанавливает собственные
правила после перезапуска компонентов. Компоненты и профили находятся на роутере.

Автозапуск проверен реальной перезагрузкой: без команды запуска с ПК
TCP и UDP заработали примерно через 75 секунд. После последующего добавления
tpws проверен перезапуск сервиса загрузочным supervisor и работа всех компонентов.
Во время загрузки до готовности сервиса интернет идёт напрямую.

В boot.sh vm.panic_on_oom меняется с 2 на 0. Процессы Xray/TUN/tpws имеют
повышенный oom_score_adj: при нехватке памяти предпочтительнее завершить
вспомогательный процесс, чем перезагружать весь роутер.

## Управление

Необязательная панель: python control.py из этой папки.
Она отправляет команды и не участвует в обработке трафика.
Текст панели обновлён, Python-код проверен компиляцией; визуальная проверка
панели в этой задаче не выполнялась.

- «Включить»: сохранённый профиль и DPI-обход.
- «Профиль 1»: первая подписка, VLESS REALITY.
- «Профиль 2»: вторая подписка, VLESS TLS.
- «Прямой интернет»: отключить Xray, TUN и tpws, снять собственный перехват.
- «Статус»: готовность процессов и правила.

Смена профиля занимает около 20–30 секунд и прерывает текущие прокси-соединения.
Выключенное состояние также сохраняется после перезагрузки.
Подписки импортированы как два готовых профиля; автообновления подписок нет.

Консоль: /bin/sh /data/mvp/mvp-service.sh on|off|profile 1|profile 2|status.
Управление Telnet разрешено только с 192.168.3.2 на br0. Если DHCP изменит
адрес управляющего ПК, потребуется поправить доступ; обычная маршрутизация
остальных устройств от адреса ПК не зависит.

Windows v2rayN и Zapret для работы этой схемы не нужны. Zapret на ПК
остановлен, но его автозапуск не менялся: не включать одновременно,
его подставной TLS SNI может мешать классификации Xray на роутере.
Системный прокси Windows выключен; пользователь удалил HTTP_PROXY/HTTPS_PROXY.

## Проверки и ограничения

Проверены оба VLESS-профиля с прозрачным TCP и UDP до изменения схемы на прямой
YouTube/голос. В итоговой схеме профиль 1: YouTube HTTP200 через dpi,
Discord API HTTP200 через proxy, example.com HTTP200 через direct.
UDP DNS к 1.1.1.1 прошёл через proxy; STUN Cloudflare прошёл через direct.
Прямой UDP к 8.8.8.8:53 и Google STUN не ответил; это не заменяется утверждением
о работоспособности всех произвольных UDP-сервисов.
Пользователь подтвердил, что голос работает в обе стороны с меньшим пингом
и видео YouTube воспроизводятся. Снижение пинга связано с прямым голосовым
маршрутом, а не с отключением iPhone.

Если процесс Xray или TUN завершается, watchdog снимает собственный перехват
и перезапускает компонент. Удалённый VLESS-сервер при живом Xray автоматически
не переключается: выбрать второй профиль или прямой интернет.
Используется старый Xray 1.8.17 (Go 1.22.5, ARMv5): современный 26.3.27
не работает из-за отсутствующего eventfd в ядре Huawei. Это экспериментальная
установка на debug-прошивке, не поддерживаемый OpenWrt.

## Файлы и возврат

Профили с секретами имеют права 600 и не входят в Git; локальные копии
лежат в игнорируемой .private/huawei-ax3-20261017 в основном checkout. Бинарники на роутере: Xray 1.8.17,
hev-socks5-tunnel 2.19.0 linux-arm32, tpws v72.13. tpws слушает только
127.0.0.1:10809, вход TUN в Xray — 127.0.0.1:10810.

Debug Telnet даёт root без пароля, поэтому служебные порты закрываются
MVP_MGMT для других устройств после запуска watchdog; штатная защита WAN
сохранена. Во время начальной загрузки этот дополнительный LAN-фильтр
ещё не установлен. Не публиковать отладочные порты наружу.

Для отключения: mvp-service.sh off. Для отключения самого автозапуска
переименовать только /patch/etc/rc.d/S99mvp после remount /patch в rw,
затем вернуть ro. Не удалять /data/mvp, пока S99mvp включён.
Запасной путь: подключить ПК напрямую к Keenetic (Ethernet работает по DHCP).
Исходный образ Huawei 11.0.5.6 сохранён в .private/huawei-ax3-20261017 в основном checkout.
